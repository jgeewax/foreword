FeaturesThe assistant

Permissions

You decide what the assistant may do without asking. Before a command runs, Foreword explains it part by part: what it is, what each piece does, and what it reaches beyond the book. When you say “always”, that becomes a rule in words you can read, find later, and take back.

What it may do without asking

There are seven kinds of action, each set to Ask, Allow or Never. Three presets set them all at once. The shield on the message box shows which one you’re on, and opens the same controls as Settings ▸ Permissions.

Ask first
The default. Asks before every change, so you see each edit first.
Edit freely
Edits, creates and renames files in the book, and changes Foreword’s settings, without asking. Asks before deleting, going outside the book, running other commands, or using the web.
Read-only
Reads and answers. Never changes anything.

The seven are: edit and create files, rename or move files, delete files, files outside this book, run other commands, search and read the web, and change Foreword’s settings. A few things don’t depend on them. It can always read the book’s files. It asks before reading a .env file. Commands that only look (ls, cat, grep, git status and 36 more) always run. Building the book never runs, because the preview already does that. Any change goes into effect in the current conversation at once.

Before a command runs

A card takes the command apart and says what it is in words: “Claude Code wants to run lint.py, a Python script in this book.” Under it, each part of the command line is labelled:

$ uv run      python   src/scripts/lint.py         17
  through uv  Python   the script, in this book    argument

Chips say what it reaches beyond the book: Uses the internet: github.com, Writes outside the book: ~/out.txt, Deletes files. A line says why it’s asking (“Asking because ‘Run other commands’ is set to Ask”), with a link to change that. Then: Allow once, Always allow lint.py…, Don’t allow.

A card often waits while you’re in another app. Coming back, one click presses its button: Foreword’s windows take the first click, as most Mac editors do. Before, the first click only brought the window forward, and it took a second to press anything.

A few more readings it does:

  • sudo rm -rf /tmp/x: sudo is labelled “as an administrator”, and every broader rule is marked dangerous.
  • curl -L -o ~/Downloads/stix.zip https://github.com/…: Uses the internet: github.com and Outside the book: ~/Downloads/stix.zip.
  • uv run python -c '…' with three lines of code: “wants to run 3 lines of Python it just wrote”, with the code shown and numbered. No rule could name it exactly, since the next one will be new, so the narrowest “always” is Any Python code it writes, through uv (uv run python -c *), with its warning: it can change any file. If the code touches book files, Ask it to edit instead refuses the command and asks the assistant to make the change as an edit, so you see each change.
  • Several commands on one line: “wants to run 3 commands. One needs you.” Each is tagged: only looks, your rule, allowed, or never allowed. Only the one that needs you is taken apart.

“Always” is a rule you can read

Always allow… lists rules from narrow to broad. For uv run python src/scripts/lint.py 17:

  1. Exactly this command.
  2. lint.py, with any arguments. Suggested: the narrowest rule that still saves you asking, and that carries no warning.
  3. Any Python script, through uv. “Runs any Python code, so it can change any file.”
  4. Anything through uv. “The same as letting it run every command.”

While you choose, the command above marks which parts the rule fixes and which it leaves open. Then pick where it applies: this task (until it ends, nothing kept), this book (until you remove it), or every book on this Mac. The confirmation says it in full: “Claude Code won’t ask again for lint.py, with any arguments, in Counting Words.”

Later, a command that ran because of a rule carries a by your rule chip. Click it: “It didn’t ask, because of a rule you made at 2:14 PM”, how many times the rule has been used, and Remove rule. Every rule is also listed in the permissions menu under Your rules, grouped by where it applies, with its use count and an ×. A rule works from the moment you make it, wherever you make it: one added in Settings or Your rules while a card is waiting answers that card, and any other it covers.

Rules are kept as plain commands, in files you can read. A rule for every book goes in ~/.foreword/settings.json. A rule for one book goes in that book’s .foreword.json, so it travels with the book.

"alwaysAllow": ["uv run python src/scripts/lint.py *"],
"neverAllow":  ["git push *"]

How a command line is checked

A rule covers one command, never a chain. Foreword splits a line the way the shell reads it: at &&, ||, ;, |, a newline, and a lone &, but not inside quotes. Every part has to be allowed on its own. With the lint.py rule above:

Runs
uv run python src/scripts/lint.py 17
ls chapters && uv run python src/scripts/lint.py 17 | tail -5
Still asks
…lint.py 17; rm -rf ~ and the same after &&, & or a newline
…lint.py $(rm -rf ~): anything inside $(…), backticks or <(…) asks
…lint.py 17 > out.txt: writing into a file asks each time (a > inside quotes, as in python -c "print(a > b)", is code, not a file)
Never runs
git status && git push, with a “never” rule for git push *
typst compile main.typ, even with a rule allowing typst *

A newline or a lone & used to be able to carry a second command past one you’d allowed. Since 0.4, every command on a line is checked on its own.

Why Foreword keeps the rules

Claude Code and Codex have permission systems of their own. Before 0.4, “always” went into those: a Bash(uv:*) rule in the book’s .claude/settings.local.json, or a prefix rule in ~/.codex/rules for every project. Foreword couldn’t show them, so you couldn’t take them back. Worse, the card said it would “run the command ‘uv’”, the folded-away command was the only clue to what uv would actually run, and an “always” for that allowed anything run through uv. And if your own Claude Code settings already allowed every shell command, nothing ever reached Foreword to ask about.

So now the assistant only ever hears “allow once”, and “always” exists only in Foreword. Claude Code is started with rules telling it to ask before every shell command, edit, read and web request. In Claude Code an ask rule beats an allow, even one in your own settings, so every request comes to Foreword. Foreword answers straight away when your rules settle it, and shows a card only when they don’t. OpenCode gets the rules attached to each session and applies them itself.

What the assistant can’t change

  • Its own permissions. Foreword’s settings tools refuse them and point to Settings. Asked to “let yourself run any command without asking”, Codex and OpenCode opened Settings ▸ Permissions for you, and Claude Code offered to.
  • Edits to the book’s .foreword.json or its .claude/ folder always ask, whatever else is allowed. Those are where rules live, so an assistant that could edit them could give itself rules.
  • In Ask, Discuss and Options, nothing changes files, whatever your rules allow. A “never” holds in every mode.

What it doesn’t do

  • A rule matches the command’s words, not what the program does. Allowing lint.py * trusts whatever lint.py does.
  • Codex runs some commands inside its own sandbox, and its own rules in ~/.codex/rules still act without asking. Foreword lists them in Settings, read-only, so you can see them.
  • A running command can’t be watched or stopped on its own yet.
  • Gemini CLI and Antigravity go through the same checks, but haven’t been tested through a signed-in conversation.
